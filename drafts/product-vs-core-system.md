# プロダクトと基幹システムの違い

## はじめに

「Salesforceを基幹システムとして導入する」「freeeで経理システムを構築する」といった話を聞くことが増えました。しかし、これらは元々「プロダクト」として開発されたものです。

プロダクトと基幹システムは何が違うのでしょうか？そして、プロダクトを基幹システムとして使うことの意味は何でしょうか？

本記事では、開発者視点から見たプロダクトと基幹システムの本質的な違いを明らかにします。

## 2つの軸で理解する

プロダクトと基幹システムの違いを理解するには、2つの独立した軸で考える必要があります。

### 軸1：開発思想の違い
**「誰の思いが主導権を握っているか」**

### 軸2：利用形態の違い
**「どのような役割でシステムが使われているか」**

重要なのは、これらの軸は**排他的ではない**ということです。同じソフトウェアが、両方の性質を同時に持つことができます。

## 開発思想の違い

### プロダクト：作り手主導の価値提供

**自社プロダクト**とは、開発会社が考える価値をソフトウェアに込めて市場に提供するものです。

**特徴：**
- 開発会社の哲学・ビジョンが色濃く反映
- 「こんな課題を、こんな方法で解決したい」という作り手の思想
- ユーザーは作り手の世界観を受け入れて利用

**具体例：**
- **Slack**: チームコミュニケーションを変革したいという思想
- **Notion**: 情報整理の新しい体験を提供したいという価値観
- **Figma**: デザインコラボレーションを再定義したいというビジョン

### 基幹システム：利用者主導の要求実現

**基幹システム開発**では、利用者（企業）の業務要件や思想を技術的に実現することが目的です。

**特徴：**
- 利用者企業の業務フローや経営方針が設計の根幹
- 「うちの業務に合わせて作ってください」という要求
- 開発者は要求を技術的に実現する役割

**具体例：**
- 会社固有の承認フローを実装
- 既存の業務ルールをシステム化
- 企業の組織構造に合わせたカスタマイズ

## 利用形態の違い

### プロダクト：標準化された価値提供

**市場で販売される標準製品**として位置づけられます。

**特徴：**
- 多くの企業で共通して使える汎用的な機能
- パッケージ化された製品
- 選択・導入・契約の対象

### 基幹システム：事業活動の統制と記録

**企業の事業活動を支える仕組み**として機能します。

**特徴：**
- 会社の業務プロセスの一部
- 事業継続に不可欠なシステム
- 統制機能と記録機能を持つ

## 4つのパターンで整理する

2つの軸を組み合わせると、4つのパターンが見えてきます：

| | 作り手主導 | 利用者主導 |
|--|--|--|
| **標準製品** | 一般的なSaaSプロダクト<br/>（Slack、Notion等） | 利用者主導の標準製品<br/>（稀なケース） |
| **基幹用途** | プロダクトの基幹システム化<br/>（Salesforce、freee等） | 従来型の基幹システム<br/>（受託開発ERP等） |

## ゴール構造の根本的違い

### プロダクト：単一ゴール構造

プロダクトは**1つの明確な価値**に向かって設計されます。

```
レストラン予約アプリの例：
[店] → 操作 → [goal：店と客のマッチング] ← 操作 ← [客]
```

**特徴：**
- 全ての機能が統一された体験に収束
- MVPの選定が比較的明確
- 成功指標が単純（MAU、売上等）

### 基幹システム：複数ゴール構造

基幹システムは**複数の業務ゴール**を同時に満たす必要があります。

```
レストラン基幹システムの例：
                [goal_1：注文受付]
               ↗                 ↘
[店舗] ← 連携 ←                   → 連携 → [メーカー]
               ↘                 ↗
[goal_2：在庫管理]   [goal_3：請求・会計]
```

**特徴：**
- 異なる業務目的が並列に存在
- 各ゴールが独立した価値を持つ
- 成功指標が複数存在

## 開発アプローチの違い

### プロダクト開発

**MVP → 改善の一直線的進化**
- 単一の価値仮説を検証
- ユーザーフィードバックで改善
- 機能追加の優先順位が明確

### 基幹システム開発

**複数ゴール対応の並行開発**
- 各業務領域のMVPを並行開発
- 統合・連携の設計が重要
- 全体最適と部分最適のバランス

## 現代的な現象：プロダクトの基幹システム化

多くの企業で「プロダクトを基幹システムとして使用する」ことが起きています。

### 典型例

**Salesforce**：
- **開発思想**: Salesforce社のCRM価値提供（作り手主導）
- **利用実態**: 企業の販売管理基幹システム（基幹用途）

**freee**：
- **開発思想**: freee社の会計業務効率化思想（作り手主導）
- **利用実態**: 企業の経理基幹システム（基幹用途）

### この現象が示すもの

**企業側の変化：**
- カスタム開発よりスピードとコストを重視
- 標準的な業務プロセスへの適応意欲

**プロダクト側の進化：**
- エンタープライズ向け機能の充実
- カスタマイズ可能性の向上
- 既存システムとの連携強化

## MVPの考え方の違い

### プロダクトのMVP

**「価値を感じる最小機能」**
- レストラン予約アプリなら「店舗登録」
- サービスが成立する最小条件を満たす

### 基幹システムのMVP

**「各ゴールのMVP集合」**
- 注文受付のMVP + 在庫管理のMVP + 請求処理のMVP
- 事業が回る最小条件を各業務領域で定義

この違いにより、基幹システムでは「必要最低限」の定義がより複雑になります。

## まとめ

プロダクトと基幹システムは、対立する概念ではありません。2つの独立した軸で整理することで、現代のソフトウェア開発の複雑さを理解できます。

**重要なポイント：**

1. **開発思想**と**利用形態**は独立した軸
2. 同じソフトウェアが両方の性質を持ちうる
3. **ゴール構造**が開発アプローチを大きく左右する
4. 現代では「プロダクトの基幹システム化」が一般的

開発者としては、自分が作っているものがどの象限に位置するかを意識することで、適切な開発手法や成功指標を選択できるようになるでしょう。

**「作り手の思想を込めた価値提供」**と**「事業活動の統制と記録」**、この2つの視点を使い分けることが、現代のソフトウェア開発における重要なスキルといえます。
